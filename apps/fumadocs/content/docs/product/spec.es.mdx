## Cómo funciona, en lenguaje sencillo

Una aplicación Next.js 16 se ejecuta en Google Cloud Run en [https://wovain.com](https://wovain.com). Sirve el sitio web, una API y un servidor MCP al que se conecta ChatGPT. El sitio web y ChatGPT llaman a los mismos procedimientos de la API, así que siempre hacen lo mismo. Una base de datos PostgreSQL en Cloud SQL recuerda usuarios, ideas, diseños, aprobaciones y ejecuciones de autopilot.

Cuando el vendedor pide ideas, la API pregunta a Qloo quién compraría y qué temas le gustan, y pregunta a Tavily qué hay en las noticias dentro de esos temas. Los diseños se crean con fal para productos de Fourthwall. Nemotron, alojado en Nebius Token Factory, evalúa cada diseño; después el código vuelve a comprobar las reglas que puede decidir por sí mismo. Al aprobar, la API crea los productos de Fourthwall y los anuncios de Meta, siempre en pausa. La documentación vive aparte en [https://docs.wovain.com](https://docs.wovain.com).

Por qué no algo más elaborado: una aplicación y una API mantienen pequeña la prueba de concepto y coherentes las dos superficies.

## El recorrido principal a través del sistema

Ref. PRD: `prd.md > The Core Journey`.

1. El vendedor inicia sesión → Better Auth (`/api/auth`) crea una sesión en PostgreSQL.
2. El vendedor introduce una semilla → la página web o la herramienta MCP llama a un procedimiento oRPC en `/api/rpc` → el procedimiento llama a Qloo y luego a Tavily → las ideas ordenadas se guardan y se devuelven.
3. El vendedor elige ideas → los diseños se generan con fal y se valoran con datos del catálogo de Fourthwall → se guardan.
4. Cada diseño va a Nemotron en Nebius → la respuesta se comprueba con Zod → el código aplica las reglas de impresión → el veredicto se guarda y se muestra.
5. El vendedor aprueba → el procedimiento crea los productos de Fourthwall con la conexión del vendedor.
6. Los conceptos de anuncio se generan y aprueban → el procedimiento crea una campaña, un conjunto de anuncios y anuncios de Meta, todos en pausa.
7. El vendedor ve el resultado y abre el Administrador de anuncios de Meta para iniciar la campaña.

## Dónde se ejecuta y cómo probarlo

- **Producción:** Cloud Run en [https://wovain.com](https://wovain.com); docs en [https://docs.wovain.com](https://docs.wovain.com).
- **En local:** Node.js (consulta `.nvmrc`), pnpm y Docker para PostgreSQL.

```bash
pnpm install
docker compose up -d
pnpm run dev
```

Abre la aplicación web, regístrate y sigue el flujo del vendedor; la documentación corre en el puerto 4000. Las claves van en los valores de los `.env.schema` de cada aplicación: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DATABASE_URL`, `NEBIUS_API_KEY`, `QLOO_API_KEY`, `TAVILY_API_KEY`, `FAL_KEY`. Nunca hagas commit de valores reales.

El envío requiere un vídeo de demostración corto y el repositorio público; el despliegue es adicional. URL del vídeo: por añadir. URL del repositorio: por añadir.

## Aspecto y tono

Cálido, sencillo, números primero; voz de entrenador. Temas claro y oscuro a partir de los tokens de shadcn; tarjetas amplias para las aprobaciones; una acción principal por tarjeta. Funciona en ancho de móvil.

## Componentes

### Aplicación web (`apps/web`)

Páginas, componentes de servidor, `/api/rpc`, `/api/auth` y el servidor MCP. Ref. PRD: `prd.md > Screens and Layout`.

### API (`packages/api`)

Routers oRPC. `publicProcedure` añade el registro de evlog; `protectedProcedure` exige además una sesión. Ref. PRD: `prd.md > Features and Behavior`.

### Autenticación (`packages/auth`)

`createAuth` construye Better Auth sobre la base de datos de Drizzle. Ref. PRD: `prd.md > States and Boundaries`.

### Base de datos (`packages/db`)

Esquema de Drizzle, relaciones y cliente. Ref. PRD: `prd.md > States and Boundaries`.

### Capa de decisión

Llamada a Nemotron, validación con Zod, límites impuestos por el código, eventos de decisión. Ref. PRD: `prd.md > Features and Behavior` (Autopilot).

### Flujos de Duo

Flujos de autorreparación, explorador y desarrollo alrededor del repositorio; definiciones en `docs/flows.md`. Ref. PRD: `prd.md > Features and Behavior` (After deploy).

## Modelo de datos

| Dato | Dónde | Se actualiza | Al volver |
| --- | --- | --- | --- |
| Usuarios, sesiones, cuentas | Tablas de Better Auth en `packages/db/src/schema/auth.ts` | Registro, inicio de sesión | La cookie de sesión restaura al usuario |
| Conexiones | PostgreSQL | Al conectar | Se reutilizan en cada ejecución |
| Ideas, diseños, aprobaciones | PostgreSQL | En cada paso | Una ejecución se reanuda donde se detuvo |
| Ejecuciones y eventos de decisión | PostgreSQL, por clave de ejecución | En cada decisión del autopilot | Auditables después |

Las migraciones se generan con `pnpm run db:generate`.

## Modos de fallo importantes

- **Una respuesta del modelo no se puede analizar** → el diseño se muestra sin la comprobación del modelo y se registra el error.
- **Un proveedor está caído o sin configurar** → el paso lo indica y la ejecución se pausa o continúa sin él.
- **Un límite se superaría** → el paso no se inicia y el registro de decisiones explica por qué.

## Qué se simplificó y por qué

- **Una sola aplicación** en lugar de servicios separados de API y MCP — una sola API mantiene coherentes las superficies. Separarlos añadiría despliegue y autenticación.
- **Campañas en pausa** en lugar de lanzamientos en vivo — elimina el riesgo de gasto involuntario.
- **Sin optimizador** en lugar de ajuste automático — primero hacen falta datos reales de gasto.

## Decisiones y asuntos abiertos

- El código impone los límites y Nemotron decide dentro de ellos — elegido para que un error del modelo no pueda sobrepasar el presupuesto; el coste es corregir a veces una buena respuesta del modelo.
- Qloo antes que Tavily — el gusto acota la búsqueda de noticias; el coste es depender de la cobertura de Qloo para la semilla.
- Abierto: ruta del conector de ChatGPT y OAuth en el dominio de producción (heredado de `prd.md > Open Questions`); alcance de la revisión de la app de Meta.
- Concepto poco familiar tratado: la diferencia entre un modelo que sugiere un precio y un código que garantiza un precio mínimo. Aclarado con la regla de que las comprobaciones decididas por el código sobrescriben la salida del modelo, que se mostrará con una prueba durante la construcción.
