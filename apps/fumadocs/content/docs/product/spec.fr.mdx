## Comment ça marche, en langage simple

Une application Next.js 16 s'exécute sur Google Cloud Run à [https://wovain.com](https://wovain.com). Elle sert le site web, une API et un serveur MCP auquel ChatGPT se connecte. Le site web et ChatGPT appellent les mêmes procédures d'API : ils font donc toujours la même chose. Une base PostgreSQL sur Cloud SQL mémorise les utilisateurs, idées, designs, approbations et exécutions d'autopilot.

Quand le vendeur demande des idées, l'API demande à Qloo qui achèterait et quels thèmes ces personnes aiment, et demande à Tavily ce qui est dans l'actualité à l'intérieur de ces thèmes. Les designs sont créés avec fal pour des produits Fourthwall. Nemotron, hébergé sur Nebius Token Factory, évalue chaque design ; le code revérifie ensuite les règles qu'il peut trancher lui-même. À l'approbation, l'API crée les produits Fourthwall et les publicités Meta, toujours en pause. La documentation vit séparément sur [https://docs.wovain.com](https://docs.wovain.com).

Pourquoi pas quelque chose de plus élaboré : une application et une API gardent la preuve de concept petite et les deux surfaces cohérentes.

## Le parcours principal à travers le système

Réf. PRD : `prd.md > The Core Journey`.

1. Le vendeur se connecte → Better Auth (`/api/auth`) crée une session dans PostgreSQL.
2. Le vendeur saisit une graine → la page web ou l'outil MCP appelle une procédure oRPC sur `/api/rpc` → la procédure appelle Qloo, puis Tavily → les idées classées sont stockées et renvoyées.
3. Le vendeur choisit des idées → les designs sont générés avec fal et chiffrés à partir des données du catalogue Fourthwall → stockés.
4. Chaque design va à Nemotron sur Nebius → la réponse est vérifiée avec Zod → le code applique les règles d'impression → le verdict est stocké et affiché.
5. Le vendeur approuve → la procédure crée les produits Fourthwall via la connexion du vendeur.
6. Les concepts publicitaires sont générés et approuvés → la procédure crée une campagne, un ensemble de publicités et des publicités Meta, tous en pause.
7. Le vendeur voit le résultat et ouvre le gestionnaire de publicités Meta pour lancer la campagne.

## Où cela s'exécute et comment l'essayer

- **Production :** Cloud Run sur [https://wovain.com](https://wovain.com) ; docs sur [https://docs.wovain.com](https://docs.wovain.com).
- **En local :** Node.js (voir `.nvmrc`), pnpm et Docker pour PostgreSQL.

```bash
pnpm install
docker compose up -d
pnpm run dev
```

Ouvrez l'application web, créez un compte et suivez le parcours vendeur ; la documentation tourne sur le port 4000. Les clés vont dans les valeurs des `.env.schema` de chaque application : `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DATABASE_URL`, `NEBIUS_API_KEY`, `QLOO_API_KEY`, `TAVILY_API_KEY`, `FAL_KEY`. Ne commitez jamais de vraies valeurs.

La soumission exige une courte vidéo de démo et le dépôt public ; le déploiement s'y ajoute. URL de la vidéo : à ajouter. URL du dépôt : à ajouter.

Chaleureux, simple, chiffres d'abord ; voix de coach. Thèmes clair et sombre issus des tokens shadcn ; cartes aérées pour les approbations ; une action principale par carte. Fonctionne en largeur de téléphone.

## Composants

### Application web (`apps/web`)

Pages, composants serveur, `/api/rpc`, `/api/auth` et le serveur MCP. Réf. PRD : `prd.md > Screens and Layout`.

### API (`packages/api`)

Routeurs oRPC. `publicProcedure` ajoute la journalisation evlog ; `protectedProcedure` exige en plus une session. Réf. PRD : `prd.md > Features and Behavior`.

### Authentification (`packages/auth`)

`createAuth` construit Better Auth sur la base Drizzle. Réf. PRD : `prd.md > States and Boundaries`.

### Base de données (`packages/db`)

Schéma Drizzle, relations et client. Réf. PRD : `prd.md > States and Boundaries`.

### Couche de décision

Appel à Nemotron, validation Zod, limites imposées par le code, événements de décision. Réf. PRD : `prd.md > Features and Behavior` (Autopilot).

### Flows Duo

Flows d'auto-réparation, d'éclaireur et de développeur autour du dépôt ; définitions dans `docs/flows.md`. Réf. PRD : `prd.md > Features and Behavior` (After deploy).

## Modèle de données

| Donnée | Où | Mise à jour | Au retour |
| --- | --- | --- | --- |
| Utilisateurs, sessions, comptes | Tables Better Auth dans `packages/db/src/schema/auth.ts` | Inscription, connexion | Le cookie de session restaure l'utilisateur |
| Connexions | PostgreSQL | À la connexion | Réutilisées à chaque exécution |
| Idées, designs, approbations | PostgreSQL | À chaque étape | Une exécution reprend là où elle s'est arrêtée |
| Exécutions et événements de décision | PostgreSQL, indexés par clé d'exécution | À chaque décision d'autopilot | Auditables ensuite |

Les migrations sont générées avec `pnpm run db:generate`.

## Modes de défaillance importants

- **Une réponse de modèle n'est pas analysable** → le design est présenté sans la vérification du modèle et l'erreur est journalisée.
- **Un fournisseur est en panne ou non configuré** → l'étape le signale et l'exécution se met en pause ou continue sans lui.
- **Une limite serait dépassée** → l'étape ne démarre pas et le journal des décisions explique pourquoi.

## Ce qui a été simplifié et pourquoi

- **Une seule application** plutôt que des services API et MCP séparés — une seule API garde les surfaces cohérentes. Les séparer ajouterait du déploiement et de l'authentification.
- **Des campagnes en pause** plutôt que des lancements en direct — supprime le risque de dépense involontaire.
- **Pas d'optimiseur** plutôt qu'un réglage automatique — il faut d'abord de vraies données de dépenses.

## Décisions et points ouverts

- Le code impose les limites et Nemotron décide à l'intérieur — choisi pour qu'une erreur du modèle ne puisse pas dépasser le budget ; le compromis est de corriger parfois une bonne réponse du modèle.
- Qloo avant Tavily — le goût restreint la recherche d'actualité ; le compromis est la dépendance à la couverture de Qloo pour la graine.
- Ouvert : chemin du connecteur ChatGPT et OAuth sur le domaine de production (repris de `prd.md > Open Questions`) ; périmètre de la revue d'application Meta.
- Concept peu familier abordé : la différence entre un modèle qui suggère un prix et un code qui garantit un prix plancher. Clarifié par la règle selon laquelle les contrôles tranchés par le code écrasent la sortie du modèle, à démontrer par un test pendant la construction.
