## Cómo funciona, en lenguaje sencillo

Una sola app Next.js 16 se ejecuta en Google Cloud Run en [https://wovain.com](https://wovain.com). Sirve el sitio web, una API y un servidor MCP al que se conecta ChatGPT. El sitio web y ChatGPT llaman a los mismos procedimientos de la API, así que siempre hacen lo mismo. Una base de datos PostgreSQL en Cloud SQL recuerda usuarios, conexiones, ejecuciones, ideas, diseños, productos, campañas y uso.

Cuando un diseñador describe una colección, la API pregunta a Qloo qué temas le gustan a su público y a Tavily qué hay en las noticias y en los marketplaces dentro de esos temas. Nemotron, alojado en Nebius Token Factory, escribe el brief de diseño y la ficha; fal dibuja el arte en la propia cuenta de fal del diseñador (en curso; hoy la clave de la plataforma); Nemotron lo evalúa y el código vuelve a comprobar el tamaño de impresión. Al aprobar, la API crea un producto oculto de Fourthwall en la tienda del diseñador y, después, una campaña de Meta en su cuenta publicitaria, siempre en pausa.

Hoy cada ejecución es una cadena de llamadas a funciones dentro de una sola petición web. El objetivo, en curso, es Mastra: cada paso se convierte en un paso de workflow de Mastra, la aprobación es una suspensión del workflow que se reanuda cuando el diseñador decide, las ejecuciones se guardan en Postgres para sobrevivir a reinicios y los scorers de Mastra puntúan cada agente y paso. La facturación (en revisión) cobra los pasos de pago en créditos mediante Polar.

Por qué esta forma: una sola app y un único conjunto de procedimientos mantienen idénticas las dos superficies; un solo framework de agentes (Mastra) sustituye la orquestación, la durabilidad, la memoria, las evaluaciones y las trazas hechas a mano.

## El recorrido principal a través del sistema

Ref. del PRD: `prd.md > The Core Journey`.

1. El diseñador inicia sesión → Better Auth (`/api/auth`, Google o correo) crea una sesión en PostgreSQL. ChatGPT, en cambio, inicia sesión mediante el servidor OAuth de Better Auth y llama a `POST /api/mcp` con un token de acceso.
2. Conecta proveedores → `/api/connections/[provider]/start` y `callback` ejecutan el OAuth del proveedor; `packages/core/src/sealing.ts` sella los tokens en `connection`.
3. Describe una colección → la página o la herramienta MCP `research_trends` llama a `ideas.research` → `researchIdeas` (`packages/api/src/flow/ideas.ts`) usa Qloo y Tavily desde `packages/core` → se guardan las ideas clasificadas. Los pasos de pago se miden (`flow/spend.ts`; créditos en la MR !116).
4. Elige una idea → `designs.generate` (`generateDesign`) → brief de Nemotron (`draftBrief`), arte de fal (`createArtist`), precio (`priceFor`), juez Nemotron (`judgeDesign`) → el diseño se guarda como `pending_approval`.
5. Aprueba → `designs.approve` (`decideDesign`). Objetivo: el workflow de Mastra de la ejecución se suspende aquí y `resume()` lo continúa.
6. `products.create` (`createDesignProduct`) llama a Fourthwall mediante la conexión sellada; `products.publish` lo hace público.
7. `campaigns.create` (`createProductCampaign`) → texto del anuncio de Nemotron (`writeAdCopy`) → `stagePausedCampaign` crea la campaña, el conjunto de anuncios y los anuncios en pausa en Meta.
8. `runs.start` (`startRun`) encadena estos pasos; con `autopilot: true` Nemotron elige la idea (`pickIdea`) y revisa el diseño (`reviewDesign`). Objetivo: `runs.start` crea la ejecución, inicia el workflow de Mastra y responde al instante; los clientes consultan `runs.get`.

## Dónde se ejecuta y cómo probarlo

- **Producción:** Cloud Run en [https://wovain.com](https://wovain.com); documentación en [https://docs.wovain.com](https://docs.wovain.com). La CI despliega al fusionar en `main` y ejecuta antes las migraciones.
- **ChatGPT:** añade un conector con la URL `https://mcp.wovain.com/api/mcp`. El descubrimiento OAuth se sirve en `/.well-known/oauth-protected-resource` y `/.well-known/oauth-authorization-server`; el diseñador inicia sesión y aprueba el acceso en la página de consentimiento.
- **En local:** Node.js (ver `.nvmrc`), pnpm y Docker para PostgreSQL.

```bash
pnpm install
docker compose up -d
pnpm run dev
```

Las claves se declaran en `apps/web/.env.schema`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DATABASE_URL`, `TOKEN_ENCRYPTION_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`, `NEBIUS_API_KEY`, `QLOO_API_KEY`, `TAVILY_API_KEY`, `META_APP_ID`, `META_APP_SECRET`, `NEXT_PUBLIC_POSTHOG_KEY`; la facturación añade `POLAR_ACCESS_TOKEN`, `POLAR_WEBHOOK_SECRET`, `POLAR_ENVIRONMENT`. Nunca hagas commit de valores reales.

La entrega necesita un vídeo de demostración corto y el repositorio público: [https://github.com/sami-m-g/wovain](https://github.com/sami-m-g/wovain) (MIT). URL del vídeo: se añadirá después de subirlo.

## Aspecto y tono

Editorial, contenido, primero los números (`prd.md > Look and Feel`). Temas claro y oscuro con los tokens de shadcn; una acción principal por pantalla; líneas finas y espacio generoso; funciona en el ancho de un móvil. El sistema visual está en `apps/web/DESIGN.md`. Nada de nombres de modelos ni protocolos en los textos para usuarios. El logo solo se muestra mediante `<Logo/>`; el logotipo «Impression» es la recomendación de la ronda 6, no el definitivo.

## Componentes

### Aplicación web (`apps/web`)

Páginas de marketing (inicio, guías, casos de uso, integraciones; precios en revisión), páginas de autenticación (`login`, `sign-up`, `reset`, `consent`), el `dashboard`, `/api/rpc`, `/api/auth`, `/api/mcp`, `/api/connections/[provider]/start` y `callback`, `/api/checkout/quote` y las rutas OAuth `.well-known`. Ref. del PRD: `prd.md > Screens and Layout`.

### API (`packages/api`)

`appRouter` en `src/routers/index.ts` incluye `ideas`, `designs`, `products`, `campaigns`, `runs` y `connections`; la lógica de los pasos está en `src/flow/*`. `protectedProcedure` exige una sesión o un usuario MCP; `funnelProcedure` envía eventos de embudo a PostHog. Ref. del PRD: `prd.md > Features and Behavior`.

### Servidor MCP (`packages/api/src/mcp.ts`)

`createMcpServer` registra `list_connections`, `research_trends`, `generate_design`, `approve_design`, `reject_design`, `create_product`, `publish_product`, `create_campaign`, `start_run` y `get_run`, y cada una llama al mismo router; los pasos principales también abren un widget de `packages/widgets`. Ref. del PRD: `prd.md > Screens and Layout`.

### Core (`packages/core`)

`createCore` conecta Qloo (`qloo.ts`), Tavily (`trends.ts`), Nemotron (`nemotron.ts`), fal (`fal.ts`), precios (`pricing.ts`), el juez (`design.ts`), las puntuaciones de ideas (`score.ts`), el autopilot (`autopilot.ts`), los anuncios (`ads.ts`), Fourthwall (`fourthwall.ts`), el cliente OAuth MCP remoto (`upstream.ts`), los límites de gasto (`spend.ts`) y el sellado de tokens (`sealing.ts`). Ref. del PRD: `prd.md > Features and Behavior`.

### Motor de Mastra (en curso)

Una instancia de Mastra con almacenamiento en `@mastra/pg` (la misma base de datos de Cloud SQL, con su propio esquema). Agentes: redactor del brief, juez, redactor de anuncios, revisor del autopilot. Las herramientas envuelven los proveedores de `packages/core` (Qloo, Tavily, fal, Fourthwall, Meta). El workflow de ejecución encadena investigación → diseño → juez → aprobación (suspensión, reanudación con la decisión del diseñador o la revisión del autopilot) → producto → publicación → campaña; cada paso es idempotente para que un reintento no duplique objetos externos. La memoria guarda la dirección del diseñador y sus decisiones anteriores. Ref. del PRD: `prd.md > Runs, approval and autopilot`.

### Calidad (previsto con Mastra)

Scorers de Mastra en cada agente y paso: scorers de código (tamaño de impresión, nombres evitados, límites de longitud, precio mínimo) y jueces LLM calibrados con un conjunto etiquetado. Salvaguardas de entrada y salida como procesadores de Mastra. Las puntuaciones se guardan con la ejecución, se trazan y se envían a PostHog como `agent_score`. Ref. del PRD: `prd.md > Quality`.

### Facturación (`packages/billing`, en revisión)

Planes en `src/plans.ts` (Free, Studio, Label y un paquete de créditos; las cifras son una propuesta), cargados en Polar con `pnpm polar:seed`. Un libro de créditos atómico reserva créditos antes de un paso de pago y los liquida o devuelve después. Los webhooks de Polar se reflejan una sola vez cada uno. Ref. del PRD: `prd.md > Billing and credits`.

### Autenticación (`packages/auth`)

`createAuth` construye Better Auth sobre la base de datos de Drizzle con Google, correo, JWT y MCP; `mcpResource` es la URL a la que se vinculan los tokens de acceso. Se envía un evento `sign_up` a PostHog. Ref. del PRD: `prd.md > Sign-in and accounts`.

### Base de datos (`packages/db`)

Tablas de Better Auth en `src/schema/auth.ts` (generadas); tablas del vendedor en `src/schema/seller.ts`. Ref. del PRD: `prd.md > States and Boundaries`.

## Modos de fallo importantes

- **Falta una clave de proveedor** → el paso falla con `NOT_CONFIGURED` nombrando la variable; los demás pasos siguen funcionando.
- **Un diseñador no ha conectado Fourthwall o Meta** → la herramienta MCP devuelve el error, el motivo, la solución y el enlace de conexión.
- **Un paso falla en una ejecución** → la ejecución queda `failed` con su paso y su error; con la facturación, los créditos reservados se liberan.
- **La instancia se reinicia a mitad de una ejecución** → hoy la ejecución puede quedarse en `running`; con Mastra, el workflow se reanuda desde su último paso guardado (en curso).

## Qué se simplificó y por qué

- **Una sola app** en lugar de servicios separados de API y MCP — un único conjunto de procedimientos mantiene coherentes las superficies.
- **Campañas en pausa** en lugar de lanzamientos en vivo — elimina el riesgo de gasto no deseado.
- **Tres diseños por ejecución, una prenda cada uno** en lugar de un conjunto de varios productos — el comerciante compara opciones y aprueba uno o más; varias prendas por diseño llegarán después.
- **Las ejecuciones dentro de la petición** hasta que llegue la migración a Mastra — simple, pero limitado por el tiempo de espera de la petición.
- **Un usuario por cuenta** en lugar de organizaciones — suficiente para un diseñador solo; las marcas con puestos vendrán después.
- **Sin optimizador** — primero necesita datos reales de gasto.

## Decisiones y asuntos abiertos

- El código pone los límites y Nemotron decide dentro de ellos — para que un error del modelo no pueda publicar un diseño sin comprobar ni gastar dinero; el compromiso es que a veces se descarta una buena respuesta del modelo.
- Mastra en lugar de un motor hecho a mano o un motor de ejecución duradera aparte — el fundador eligió un solo framework para agentes, workflows, memoria, scorers y trazas; el compromiso es depender del almacenamiento y del ritmo de versiones de Mastra.
- Polar en lugar de Stripe directamente — el comerciante registrado gestiona el impuesto sobre las ventas y las facturas; el compromiso es la comisión de Polar.
- Conectores del comerciante para fal, Meta y Fourthwall; Nebius, Tavily y Qloo a cargo de wovain — coincide con quién es dueño del resultado y mantiene corta la incorporación.
- OpenSpec para especificaciones y cambios — cada cambio funcional empieza como un cambio de OpenSpec vinculado a un issue de GitHub; estos tres documentos siguen siendo el resumen en formato Basics.
- Resuelto: ChatGPT se conecta a `https://mcp.wovain.com/api/mcp`; el plugin MCP de Better Auth es el servidor OAuth y `requireMcpAuth` verifica cada token.
- Abierto: cerrar los precios; licencia comercial de Qloo; alcance de la revisión de la app de Meta; conector de fal antes de activar la facturación.
- Concepto poco familiar tratado: la diferencia entre que un modelo sugiera un valor y que el código lo garantice. Se aclaró con la regla de que las comprobaciones que decide el código (tamaño de impresión, precio mínimo, rango de presupuesto) no son salida del modelo, como muestran las pruebas de `packages/core/src/design.test.ts`. La misma idea se extiende ahora a los scorers: los scorers de código son hechos; los jueces LLM se calibran antes de confiar en ellos.
