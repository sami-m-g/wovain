---
title: Nebius and Nemotron
description: How wovain uses NVIDIA Nemotron on Nebius Token Factory to write briefs, judge designs, write ad copy and decide in autopilot.
---

Wovain calls **NVIDIA Nemotron 3.5 Super VL** (`nvidia/Nemotron-3.5-Super-VL`, the `NEMOTRON_MODEL` env var, set per environment in Pulumi config) on **Nebius Token Factory**. The endpoint is OpenAI-compatible: `NEBIUS_BASE_URL`, `https://api.tokenfactory.nebius.com/v1/` by default, authenticated with `NEBIUS_API_KEY`. Every reply is validated with a Zod schema.

Nemotron does four jobs. It never replaces the checks that code makes.

## 1. Design brief and listing

`draftBrief` turns an idea into the art prompt, title, description and garment colors. Names Qloo matched for the seed are passed as names never to print.

## 2. Design judge

`judgeDesign` receives the brief, listing and artwork facts and returns a verdict (`ready` or `revise`), a 0 to 100 score, a pass or fail check for title, description, idea fit, originality and garment (the art prompt's subject is not a garment, mockup or clothing), up to five fixes and a one-line coach note.

First, `inspectArtwork` shows the drawn PNG to **Nemotron 3.5 Super VL** (`nvidia/Nemotron-3.5-Super-VL`, `NEMOTRON_VISION_MODEL`, same key and price). It checks that the art's subject is not a garment, that it has no background and nothing is cropped, that the words it prints match the brief, and that it shows on each garment color the brief lists. Code drops the colors the art disappears on, and fails the design when none is left. These checks are facts: the text model can't overrule them.

The print-size rule is decided by code (`printFacts`, `applyFacts`): art narrower than 2880 px fails whatever the model says, and the verdict becomes `revise`.

A design the judge sends back is redrawn once, from a new brief that applies the fixes, and the redraw isn't charged again. If the redraw is still `revise`, it goes to approval flagged: the card lists the failed checks and the button reads "Approve anyway".

## 3. Ad copy

`writeAdCopy` writes up to three ad variants with an angle, a headline and a message for the Meta campaign.

## 4. Autopilot

With autopilot on, `pickIdea` chooses the most promising ranked idea and `reviewDesign` approves or rejects the design, each with a one-line reason. Code still gates the run:

| Gate | Enforced by code |
| --- | --- |
| Judge | A design the judge says to revise is never approved, whatever Nemotron says |
| Idea choice | An index the list does not have falls back to the top-ranked idea |
| Price | At least $10 profit and a 30% margin after card fees, sales tax and a refund reserve (`priceFor`) |
| Daily budget | Between $1 and $500 |
| Meta | Every object is created paused |

The reason for each decision is stored on the design, and a run records its step and any error.

## Media buying

Built and tested, but not run against a live Meta account in the demo: the judge account has no Meta connection.

- **Campaign build.** `stagePausedCampaign` in `packages/core/src/ads.ts` builds the campaign, ad sets, creatives and ads through Meta's Ads MCP (`ads_create_campaign`, `ads_create_ad_set`, `ads_create_creative`, `ads_create_ad`), every object paused. The drop's flow is `createDropCampaign` in `packages/mastra/src/mastra/flow/campaigns.ts`.
- **Qloo targeting (#161).** No campaign without a Qloo audience: `requireQlooAudience` (`flow/audiences.ts`) refuses one, and the audience sets the ad sets' ages, gender and interests and the copy's persona.
- **Pixel (#212).** On the merchant's single Meta grant, wovain finds or creates the pixel (dataset), shares it with the ad account and sends a Conversions API test event (`flow/pixel-setup.ts`, `packages/core/src/pixel-setup.ts`, flag `meta-pixel-automation`).
- **Spend rules (#141).** Every 30 minutes (`packages/core/src/ad-rules.ts`, `flow/ad-rules.ts`, flag `ads-profit-rules`): the stops pause every campaign at the daily cap, the monthly cap or the loss limit ($50 by default: ad spend minus the profit of its sales); the kills pause an ad that spends its target cost per sale with no sale, or breaks the cost-per-click or click-through limits; a raise adds at most 20% to the daily budget after 3 purchases at 1.3 times break-even ROAS, at most every 48 hours.
- **Meta backstop (#215).** The kill and stop rules are mirrored into the ad account's Automated Rules (`packages/core/src/meta-backstop.ts`, `flow/backstop.ts`, flag `meta-backstop-rules`), so Meta pauses spend even when wovain is down.
- **Nemotron agents.** Super VL writes the ad copy (`writeAdCopy`, Default job); Lightning runs the ad judges (`ad_judge`, Fast job); Ultra reviews the optimizer's proposals (`ads_optimizer_review`) and makes autopilot's calls (Reasoning job).

## 5. Docs chat

The AI chat on the docs site (`apps/fumadocs`) uses the same Token Factory endpoint and `NEBIUS_API_KEY`, with **Nemotron 3.5 Lightning** (`nvidia/Nemotron-3_5-Lightning`, the `DOCS_CHAT_MODEL` env var, $0.06 in and $0.24 out per 1M tokens). It searches the docs, then answers from three short results. To keep spend low it caps the answer at 400 tokens, sends only the last four messages, refuses empty, very long or off-topic prompts without calling the model, and limits each visitor to 10 messages per 10 minutes and 50 per day, with a global daily cap. Each call is a PostHog `$ai_generation` event with tokens and cost, and no message text.

## Models by job

With the `model-routing` flag on (development, next.wovain.com and nebius.wovain.com), each agent asks for a job and the job's env var names the model (`packages/core/src/model-router.ts`, `AGENT_ROLES` in `packages/core/src/agents.ts`). Pulumi config sets every ID per environment.

| Env var | Model ID | Used by |
| --- | --- | --- |
| `NEMOTRON_MODEL` | `nvidia/Nemotron-3.5-Super-VL` | Every agent when `model-routing` is off |
| `NEMOTRON_VISION_MODEL` | `nvidia/Nemotron-3.5-Super-VL` | The judge's vision check when `model-routing` is off |
| `NEMOTRON_MODEL_DEFAULT` | `nvidia/Nemotron-3.5-Super-VL` | `design_brief`, `ad_copy`, `idea_words`, `research_themes`, `competition_summary`, `brand_discovery`, `brand_proxies`, `drop_directions`, `drop_style`, `product_listing`, `voice_intent` |
| `NEMOTRON_MODEL_REASONING` | `nvidia/Nemotron-3-Ultra-550b-a55b` | `design_judge`, `autopilot_pick_idea`, `autopilot_review_design`, `ads_optimizer_review` |
| `NEMOTRON_MODEL_VISION` | `nvidia/Nemotron-3.5-Super-VL` | `design_vision` |
| `NEMOTRON_MODEL_FAST` | `nvidia/Nemotron-3_5-Lightning` | `ad_judge`, `brief_terms`, the Mastra scorers, the prompt-injection and PII guardrails |
| `NEMOTRON_MODEL_SAFETY` | `nvidia/Nemotron-3_5-Lightning` | Mastra moderation on what the merchant publishes |
| `DOCS_CHAT_MODEL` | `nvidia/Nemotron-3_5-Lightning` | The docs chat |
| `VOICE_STT_MODEL` | `nvidia/nemotron-asr-multilingual/asr` | Voice commands, served by fal, not Token Factory |

Tavily runs live in the same run: Search and Extract for each Qloo theme, a trademark search for every printed phrase, and Research on demand. See [Tavily](/docs/integrations/tavily).

## Why Nemotron

- A second model with a fixed rubric and a schema catches what a host agent's self-review misses.
- Structured output at a low cost per call suits several small decisions per run.
- Running the decisions on Token Factory means they do not depend on a host agent staying in the loop.

## Configuration

```bash
NEBIUS_API_KEY=...
```

Without the key, steps that need Nemotron fail with a `NOT_CONFIGURED` error naming the variable. Nothing else breaks.
